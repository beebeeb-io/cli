### Auth & session

- `bb login` — browser device authorisation; handshake crypto (P-256 ECDH + HKDF-SHA256 + AES-GCM, raw fallback for v0.4 web apps) lives in `beebeeb_core::cli_auth` (`CliEphemeralKey`/`decrypt_browser_payload`). `--headless` for SSH boxes; CLI auth sessions stored in Redis (HA-safe). The printed link carries NO code — the user TYPES the `Authorization code:` line into the approval page (a link someone else sends has nothing to approve); the WS init frame (`login.rs::init_frame`) adds `client`/`client_version`/`os`/`device_name` ("reported by the device").
- `bb signup` — does not create accounts (trial needs a payment mandate, collected only by the web checkout). Prints "Create your account at <web>/signup — then run `bb login`.", best-effort `open::that` (not when `--json`/`--quiet`/headless), exit 0. Web host from `src/web_url.rs` (`APP_URL` env, else derived from the API URL). No registration code in the CLI at all.
- **Onboarding document:** `ApiClient::get_onboarding(with_session)` reads `GET /api/v1/onboarding` (headers `X-Beebeeb-Client: cli`, `X-Beebeeb-Onboarding-Schema: 1`, `X-Beebeeb-Client-OS`, `X-Beebeeb-Store-Channel: direct`; 5 s timeout; 404/405 → `Ok(None)`). `src/account_state.rs::OnboardingDoc` is lenient (schema major 1 only; unknown → defaults). It changes words, never behaviour: `bb signup` still only points at the web; adds an explanatory line + `signup` key in `--json`; `bb whoami` shows the account state label + denied capabilities. Contracts vendored at `contracts/onboarding/` from `repos/server/contracts/onboarding/` (drift guard: `make check-onboarding-contract`; re-vendor with `cp -R`).
- `bb logout` / `bb whoami` (email, device, region, quota, account state off `GET /billing/subscription`'s `account_state`/`data_deletion_at`; `needs_plan`/`lapsed` → plan `none`, upload `blocked`, notice; exit 1 when logged out / session rejected) / `bb status` (same exit behaviour) / `bb config` (masked secrets).
- Generic 401 → "Your session expired or was revoked. Run `bb login` to sign in again." (`api::SESSION_EXPIRED_MESSAGE`; stable `unauthorized` code kept on `ApiError`). Connect failure → "Can't reach <api_url> — check your connection or --api".

### Files

- `bb push <path>` (alias `bb upload`) — v2 upload-session route (`/api/v1/uploads/*`); `--replace` sends `file_id` + `base_version_number` (version by file_id, no name byte-match); a fresh push omits `file_id`.
- `bb push <folder>` (task 2334, `commands/push_folders.rs`): writes into the folder of that name already in the target, at every level, never a second one. The name must decrypt to the same bytes through `OwnedKeyResolver` (as `bb ls` and the conflict check do, so a collaborator's folder inside a shared folder matches; a plaintext name never does). A row the resolver cannot open is one of two kinds (`OwnedKeyResolver::resolve_or_why`): `NotNow` (a server read it needs did not answer, or custody is unavailable: a later run may open it) or `Never` (everything was read and this device cannot open it on any run). A request list (`GET /file-requests`) that did not load makes an unopened row `NotNow`. In key resolution only 405/501 on `GET /shares/invites/sent` mean "no such route, no invite" (`ApiClient::list_sent_invites_for_keys`); a 404 is a read that did not answer. A `NotNow` folder row fails the lookup, even when another row matches (it may be an older same-name folder); a `Never` row is passed over. Each parent is listed once per push. Of several, the oldest (`created_at`, then smallest id); for a folder found implicitly the oldest NOT shared on its own wins, with or without `--reuse-shared` (a no stays a no); one line, after the choice, says how many and which. `--folder` uses the same lookup and the same "unshared first" rule; it reuses a shared folder only when every one of that name is shared, and says so ("no unshared one exists"); a single folder needs no share lists. Of several same-name folders, share lists that cannot be read stop the push (even with `--reuse-shared`): the unshared one cannot be told, so the oldest is never guessed. A folder found implicitly that is shared ON ITS OWN (its own invites from `GET /shares/invites/sent`, its own folder links from `GET /shares/folder-links`, its listing `share_count`) is reused only after a `y` at the terminal or with `--reuse-shared`; a no makes a new folder; no terminal, `--json` or `--quiet` refuses with exit 2. An unreadable share answer (or one without its list) stops the push; with `--reuse-shared` it is said once and not asked again that push. A 404/405/501 (no such route) is UNKNOWN, never private, and counts as shared (asked at a terminal, refused elsewhere without `--reuse-shared`): without the invite route always, since `share_count` counts public links only (server `PAGE_SHARE_COUNTS_SQL`), never people; without the folder-link route only when the row has no `share_count`, since a 501 means shared folders are off for the owner and the server then serves none of their folder links. The two GETs are sanctioned reads in `tests/shared_folder_key_writers.rs`.
- A re-push skips each file this machine already uploaded, unchanged on both sides (task 2334, `commands/push_repeat.rs`): `bb push` appends one line per finished file to `finished-uploads.jsonl` beside the resume sidecar, created 0600 because it names local paths (canonical path, size, mtime, file id, folder, the version the completion answer named; nothing when the answer names none or the mtime is a whole second, which cannot tell a same-size edit in that second from none); a same-name file is skipped and counted ("skipped N already uploaded", `total_already_uploaded` in `--json`) only when that record says this file, at its current size and mtime, went into this folder AND the server's row for the RECORDED id (the same-name file or a `--keep-both` copy beside it) is in the folder THIS push writes into (the record must name it too), not trashed, completed at that version with that plaintext size. The CLI writes no content hash a row carries, so this record is the proof; anything else (another machine's push, a changed file, a newer version, a row it cannot read) keeps the conflict rule. Applies with no flag and with `--keep-both`; `--replace` always uploads. A same-folder FILE row `find_conflict` cannot open `NotNow` fails that file when no other row matches, never "no conflict"; a `Never` row is passed over.
- A resumed create continues only into the folder it asks for (task 2334, `upload/pipeline::resumable_here`): the server fixes a new file's parent at init and keeps it at completion. The driver reads the row's parent (`GET /files/{id}`), which decides when it answers (completion puts the file there, and the web app can move the row either way); when the server cannot say, the parent a record written since 2334 holds decides (`resume::PendingEntry.destination`, serde default, so older records still load). Another folder ends the old upload with `POST /files/{id}/upload/abandon` (deletes the never-completed row, which until then is listed there and counted in the quota) and starts the file again; an unreadable answer with no recorded parent, or a failed abandon, keeps the record and fails the file for that run. `bb push` hands the row it just read (`UploadSpec.read_row`) so the driver does not read it again. Every abandon-then-clear goes through `end_interrupted` (abandon first; a failure keeps the record). `ApiClient::list_sent_invites` reads `GET /shares/invites/sent` for a push's share check (404/405/501 = `Null` = unknown); key resolution reads it through `list_sent_invites_for_keys` (405/501 = no invite; a 404, or an answer without its list, is a read that did not answer). Of several same-name folders, a folder the server does not say is private or shared (`Exposure::Unknown`) also stops the push.
- `bb push --parallel N` (1 to 8, default 4; `commands/push.rs` `PushCtl`, `upload/limits.rs`, `upload/pipeline/parallel.rs`, `api/pause.rs`, `interrupt.rs`): up to `used = min(N, 640 MiB / chunk − 3)` chunks of one file in flight at once, every chunk-sized buffer charged to a 640 MiB byte budget before it is allocated (the real heap peak is measured in a child process, `upload/pipeline/memory_tests.rs`); the chunk plan follows N, a resumed session keeps its record's `chunk_size_bytes`, an old record plans at the caller's pre-change concurrency (push 1, sync `--concurrency`); a 429 (any route) or a chunk-route 503 closes one shared pause gate per API origin that the pacer and the 429 branch wait on, one notice per pause; the push's one `Interrupt` (bound to the gate) ends a pause and drops the chunks in flight on Ctrl-C, keeps the record, prints the one interrupt line (not with `--quiet`) and exits 130, a second Ctrl-C exits at once, a `complete` in flight is waited for; a resumed session the server reports completed is finished (`push_repeat` lets a completed row the record names reach the driver), re-uploaded here under a freshly minted id only when its row is in another folder or gone. The resume record is written to a per-process temp file and renamed. `--json` `transfer` adds `parallel_asked` and `pauses`. Test builds compile dependencies at opt-level 2 (`Cargo.toml`): the 2 GiB fixtures of the goldens and the memory test. A folder push runs in two stages (PR 2, spec §7; `commands/push_file.rs`, `commands/push_schedule.rs`): stage 1 prepares every file in order without a lock (the conflict check and its question, the id, the "already uploaded" skip), so every question comes before the first byte; stage 2 uploads up to N files at once in file order, each taking its upload lock on admission and re-checking under it the resume record and the same-name row (a change fails that file: `changed while this push was preparing; run the command again`). Chunks in flight across the files ≤ N (`ChunkLimits::chunk_slot`); each upload attempt is admitted to the budget with its read buffer and one seal (R + 2 C, `ChunkLimits::admit`, a waiting attempt holds nothing), its seals draw from the pool first and from that reserve when the pool is short (a lent frame moves to the pool when it can, which keeps §4.2's worst moments), so files never deadlock on the budget; thumbnails run one at a time with a 64 MiB share. The live view keeps a share per file (`TransferStats::next_file_as`, `LiveProgress::begin_file_chunks_as`) and shows `min(N, Σ used)` of the files in flight; per-file lines print in finish order, `--json` lists input order; one interrupt line names the file in flight, or the folder when several were, and exit 130 only when a file was left undone. Spec: workspace `docs/superpowers/specs/2026-11-06-cli-push-parallel-chunks-design.md`; plan `docs/superpowers/plans/2026-11-06-cli-push-parallel-chunks.md`.
- `bb push` live transfer numbers (task 2333, `transfer_stats/` the numbers, `transfer_view/` the lines, `commands/push_report.rs` the push's plan and end lines): on a terminal (stdout AND stderr), a bar line with percent, bytes, current Mbps and ETA plus the file line; `-v/--verbose` adds a stats line (chunks done/total, in flight now/limit, average), a pool line (the storage COUNTRY only, Guus 2026-11-06: never the pool id, a city, a datacenter code, a host or a provider; nothing when the answer names no country; `--json` `pools` the same: country and code, no id, lead 2026-11-06), and one line per chunk on stderr (also on a pipe, so `2>log` keeps them; coloured only when both streams are terminals) plus a detail line under the summary. `-v` with `--quiet` is a usage error (exit 2, checked in `main` after parsing, either order); with `--json` it has no effect: the JSON always carries `transfer` (spec §7 keys). Every line printed mid-run goes through the sink (`ChunkProgress::note`/`suspend`; code without a sink, the API's rate-limit pause, through `transfer_view::notice::stderr`). Units everywhere: decimal Mbps with one decimal (`ui::human_speed_network`), durations as `7m 21s`. Each file is announced before its upload (`TransferStats::next_file`) and its end settles its share (`end_file`: kept, taken out when not sent, the unsent part given up when failed); its share follows the size the driver reads when the file begins (`begin_file`), so a file that changed after the plan, even during its conflict prompt, never takes done past total (I1). The average and the summary's total (and `--json` `transfer.duration_ms`/`avg_mbps`) leave out the time spent waiting on the person (a prompt run in `suspend`; the lead, 2026-11-06), so `avg × total = bytes` holds. Spec: workspace `docs/superpowers/specs/2026-11-06-cli-push-live-transfer-stats-design.md`.
- `bb pull <id-or-path>` — streaming download + decrypt (constant memory); legacy decrypt preserved (JSON-blob chunks, pre-`bb repair` binary-UUID files → buffered path). **Never silently overwrites**: `-f/--force` overwrites; a rich TTY gets `y/N`; non-interactive runs refuse with non-zero exit naming `--force`/`-o`. Guarded before any bytes download (`tests/pull_overwrite.rs`). Folder pulls guard only file-request uploads (attacker-named file must not replace a local file; skip, exit 3).
- Upload/share refused by account state: `409 plan_required | account_lapsed` (older: `413 quota_exceeded`) → typed messages via `explain_account_refusal` (cached once per `ApiClient`; happy path pays no extra round-trip). `bb push` pre-flight `check_quota`.
- `bb ls [path]` / `bb mv <src> <dst>` (shared `ApiClient::move_file` parent is tri-state: `None` unchanged, `Some(None)` root null, `Some(Some(uuid))` folder; only an explicit root destination may send null; folder repair omits the parent) / `bb quota`.
- `bb region [list|get|set <europe|country>]` — where NEW uploads are stored, by COUNTRY (`europe` = default, no specific country). The choices come from `GET /api/v1/storage-regions`, never from the binary; `set` sends the row's `id` verbatim and refuses a non-`selectable` (coming soon) row or an unknown name without sending a request. **No city is ever printed**, in any command, whichever server answers (guards `tests/no_city_copy.rs`, `tests/region_choice.rs`). Detail (legacy datacenter ids, older-server folding, `--json` keys): docs/runbook/cli-task-history.md.

### Sharing

- `bb share <path-or-id>` (`--expires`, `--max-opens`, `--passphrase`) — always double-encrypted, web wire format (`src/commands/share.rs`): `wrapped_file_key` = STANDARD base64 of `nonce(12) || AES-256-GCM(raw K_c, FileKey)` (no KDF, no AAD; pinned by the core `share_key_wrap` KAT); link = `{APP_URL}/s/<token>#key=<base64url K_c>`; token client-minted + `owner_wrapped_key`/`owner_wrapped_token` so the owner can rebuild the link. `--passphrase` is a server-checked Argon2id gate, not encryption. `--no-double-encrypt` hidden and errors (README flags guarded by `src/readme_flags_tests.rs`).
- `bb shares` — rebuilds each link from the owner blobs ("link not stored" for older shares) / `bb unshare [share-id]` (interactive picker without args).

### File requests

Account-less links for uploads into your vault; crypto via core's `file_request` module (per-request X25519 keypair; private half wrapped under the master key, public half only in the link fragment). `bb request create|list|rm|send` (mints `<APP_URL>/r/<token>#<R_pub>`; `--delete` errors until the server DELETE route is live — close instead). **Key-derivation context:** the HKDF context for the private-key wrap and the per-upload seal is the EMPTY byte string (the server assigns ids only after client crypto must be done) — every client must use the same constant (module docs in `src/commands/request.rs`).

### Sync & mount

- `bb sync <local> [remote]` — bidirectional, continuous (`--once`, `--daemon`, `--stop`, `--dry-run`, `--force`, `--delete`, `--concurrency`, `--rehash`, `--allow-mass-delete`, `--rebind`); v2 streaming uploads. **Sync never deletes on absence (deletion-safety spec R4/R5):** a file missing from the remote listing is not a deletion — local removal only when the server's own record says `is_trashed` (confirmed tombstones), the file is byte-identical to the manifest, the listing is trustworthy (`ListingHealth`, no truncation, remote root matches `.bb-sync.json` or `root_unreconciled` blocks until `--rebind`), and under the mass-delete breaker (max(50, 10% of tracked); over it nothing is removed, exit 3, daemon never gets `--allow-mass-delete`). Removal is a MOVE into `.bb-trash/<UTC stamp>/<rel>`, never an unlink. An undecryptable download leaves the remote untouched, writes nothing locally, is reported, exit 3. (details: docs/runbook/cli-task-history.md)
- `bb watch` — deprecated alias for `bb sync`.
- `bb mount` — FUSE, `--features fuse` only; release binaries ship WITHOUT FUSE (hidden, stub exits 1 → `bb webdav`; pinned by `tests/mount_availability.rs`) / `bb unmount` / `bb webdav` (`--port`, `--read-only`, `--cache-ttl`, `--no-cache`, `--verbose`).

### Backups (LD-0113, `src/backup/`, `src/backup_guard.rs`)

- **The rule (spec Amendments 8/8a):** a device's backup is written by its own backup pass only. `rm`/`mv`/`mkdir`/`push` ask core's `check_app_mutation` with the row's `BackupPosition` (depth below the row flagged `system_role = "backups_root"`: `ResolvedPath.backup_depth` on a walk down, `backup_guard::depth_of` through `GET /files/{id}` parents for an id). `bb push` keeps one `BackupDepths` per command: a folder it found in a listing it read, or made itself, needs no read; each folder above a `--parent` is read once; a parent it cannot read (a 5xx, or a 403/404 on the destination itself) stops the push with that reason (fail closed). Refusals print core's words; Create/Write add `backup_guard::BACKUP_HINT`. A server `409 protected_folder` prints core's root words (`server_refusal`), never the server's text. `bb rm` of a device/category folder asks the §8 question (only `--yes` answers it, never `-f`/`--force`, which skip the soft-trash prompt only; no terminal → exit 2). `bb ls`: `[Read-only]` (`MSG_BADGE`) on the root, `.device.json` never listed. Tests: `tests/protected_backups.rs`.
- **`bb backup add|remove|list|run|status`:** `beebeeb_backup::run_pass` with `backup::host::CliHost` as the `BackupHost`; uploads drain after the pass through `upload::stream_encrypt_upload` with the `ChunkProgress::before_complete` fingerprint guard (a file changed mid-read is abandoned, never completed). Every request goes through `ApiClient::for_backup()` (`X-Beebeeb-Origin: backup`). Device id: core `device_id_from_machine_id(/etc/machine-id)`, name from `PRETTY_HOSTNAME` (test seams `BB_BACKUP_MACHINE_ID_FILE` / `BB_BACKUP_MACHINE_INFO_FILE`), platform `cli`. Root via `PUT /api/v1/backups/root` (core `resolve_root`; duplicates are claimed, never merged). Store: `<config>/beebeeb/backup.json` (bound to the `/auth/me` id) + `backup-records-<n>.jsonl` (append per completed upload, compacted per run). A folder gone elsewhere turns off (`stop_words`, the seam for core's `backup_stop`, LD-0121); exit 4 (`exit::BACKUP_OFF`); `add` again = "Back up again". Tests: `tests/backup_command.rs`.

### Two-factor authentication

- `bb 2fa status` — reads `totp_enabled` off `GET /api/v1/auth/me` (NOT the security-score factor `has_totp || has_passkey`, which misreports passkey-only). Enabled/disabled only (no backup-codes-remaining route).

### Step-up confirm over OPAQUE

`bb trash empty`, `bb rm --permanent`, `bb account update` ask for the password and exchange it for a single-use `X-Confirm-Token` (`commands::confirm::acquire_confirm_token`). For OPAQUE accounts the plaintext password never reaches the server (confirm-opaque-start/finish; wrong password fails inside `client_login_finish` → "incorrect password"). Only `409 {"opaque_unavailable": true}` falls back to legacy plaintext `POST /auth/confirm`; never retried in plaintext otherwise. Password prompt and OPAQUE state are `Zeroizing<String>`.

### Exit codes and non-interactive runs (`src/exit.rs`)

`0` success · `1` any error · `2` a prompt was needed but stdin is not a terminal · `3` the run finished but left items failed or unresolved · `4` a backup is off (`bb backup run`/`status`, LD-0113) (`exit::with_code`). Non-interactive: `bb push` existing name → 2; `bb rm` without `-f` → 2; `bb unshare` without id → 2; `bb sync --once` with failures → 3 (`! incomplete · N failed · M ⚡`). Covered by `tests/non_interactive.rs`.

## Upload pipeline (`src/upload.rs`)

`bb push` and `bb sync` share one streaming driver: `upload::stream_encrypt_upload(api, Arc<MasterKey>, UploadSpec, &dyn ChunkProgress)` on the v2 `/api/v1/uploads/*` route (session init → `chunks/{i}` → `complete`; durable `file_id` keys the file). All direct-upload callers (webdav, mount, repair) use the same three `ApiClient` methods; the legacy `/api/v1/files/upload` route is never called by the CLI.

- **Replace** = versioning by file_id (`base_version_number`); sync/mount/webdav mint fresh ids (`None`). Init body sends plaintext `file_size_bytes`; `profile` sent as `"desktop"` with an explicit chunk plan (the server uses it verbatim); the driver asserts the response plan equals what it sent.
- **Resume** (`resume.rs`): persists `(file_id, upload_session_id)` keyed by path; unchanged size+mtime skips init and re-PUTs every chunk (v2 chunk route is idempotent: `{skipped:true}`); pre-v2 entries are non-resumable.
- **Own ids (L13, SF-0001, `item_id.rs`)**: every create (upload, folder, webdav PUT/MKCOL, mount, repair) proposes its own id and requires every init / create / completion answer to echo it byte for byte in canonical lowercase spelling (`item_id::Proposed`: a minted id must also be v4; a replace's listed row id is compared by spelling only). A mismatch fails the op with `CHANGED_ID_MESSAGE`, abandons the session it opened (by the client's id, never the echoed one) and seals nothing under the echoed id. Resume records say which write they are (`self_minted` for a create, `replaces` for a replace): a create resumes only its own, a replace only its row's; any other record is abandoned before it is cleared, and a failed abandon fails the file for that run. A completion mismatch keeps the record (the retry stays on the same id). A replaced remote is trashed only after the new copy completed (sync, mount overwrite). Tests share one loopback mock: `src/test_server.rs`.
- Consumes core's `ChunkEncryptor` in a producer task (`spawn_blocking`) feeding a bounded `tokio::mpsc` (cap 1); constant memory (peak ≈ concurrency × ~4 × chunk_size); `expected_total_ciphertext()` = size + 28·chunk_count; `finish()` guards shrink, re-stat guards size change. Cancellation via shared `AtomicBool` + `rx.close()`. Progress: the driver reports chunk events (`chunk_started`/`chunk_done`/`chunk_retried`/`chunk_settled`, an `InFlight` guard per chunk, `Held::AlreadyStored` for a chunk a resumed direct session already held, the pool from the init answer or a resumed session's completion, a `Tally` rolled back on a failed attempt) to any `ChunkProgress`; `bb push` uses `transfer_view::LiveProgress` (task 2333), `bb sync`/`bb pull` still `BarProgress` until task 2333's second PR. One chunk of a file is in flight at a time (`CHUNKS_IN_FLIGHT_PER_FILE`). Thumbnails (image/*, ≤64 MiB read) best-effort, non-fatal. `ApiClient` 300 s timeout (SSE stream 24 h). Provenance headers: `X-Beebeeb-Client: cli` + `X-Beebeeb-Client-Version: <CARGO_PKG_VERSION>` on every request (`build_client()`); the self-update checker's GitHub client intentionally does not send them.

## Server-provided names become local paths only via `src/safe_path.rs`

Names come from the server — for file-request uploads from an anonymous stranger — so `out_dir.join(name)` is never used directly:

- `safe_path::safe_child(dir, name, Rules::Portable)` (bb pull folder items): ONE plain component, no symlink target, canonical inside `dir`; unsafe item = skip + warning + exit 3, the rest still pulls.
- `safe_path::default_output_path(name)` (bb pull without `-o`): same check, failure says "pass -o <path>"; explicit `-o` is never checked.
- `bb pull --zip`: `check_component` per entry; unsafe entries left out of the archive (exit 3).
- `bb sync`: `Rules::Host` in `walk_remote` + `safe_rel_join` before local mkdir/download/unlink.
- Windows reserved names/`:`/trailing dots enforced on Windows hosts only. Covered by `tests/pull_path_traversal.rs` + unit tests.

## Download pipeline (`src/download.rs`)

`bb pull` and `bb sync`'s `download_to` share `download::stream_download_decrypt`: incremental body read + `ChunkDecryptor::push_frame`, `.tmp` + atomic rename, constant memory. Frame sizing = `total / chunk_count` (remainder last); no `X-Chunk-Size` sent. Legacy preserved (user-data safety): JSON-blob chunks and pre-`bb repair` binary-UUID files fall back to buffered `crypto::decrypt_file_chunks`. 600 s download timeout. `bb pull --zip` stays buffered by design.

**Direct S3 transfer (task 2173).** `stream_download_decrypt` first tries `direct_download::try_download`: when discovery offers `object-download-v1`, chunks come straight from object storage through grant windows via `ApiClient::storage_client()` (a client of its own: no default headers/cookies/`Authorization`, no redirects, https only), are decrypted in order and published only after `finish()`. The rules are shared pure Rust in `beebeeb_core::direct_transfer`; the CLI only does the HTTP. `--transport api` / `BB_TRANSPORT=api` force the API; `BB_TRANSPORT_TRACE=1` traces decisions (never a URL); `bb pull --json` reports `transport`. A failed direct download is a typed `DownloadError` (`Unreadable`/`Changed`/`Other`): sync decides on the type, never on message text, and a pass never aborts for an unreadable or changed file. No `launchctl`/`systemctl` call is made unless `$HOME` is the account's home (`daemon::service_manager`; override `BB_SERVICE_INSTALL_ALLOW_CUSTOM_HOME=1` for an intended custom HOME; no test may call `bb sync --daemon`). Detail: docs/runbook/cli-task-history.md → "2173 direct S3 download".

**Direct S3 upload (task 2173, `object-upload-v1`).** `stream_encrypt_upload` asks for it at init only: `X-Beebeeb-Capabilities: object-upload-v1` goes on `POST /uploads/init` and nowhere else, when discovery offers the direction and nothing forces the API (`BB_TRANSPORT=api`). The 201's `transport` says what the server chose; a server that does not answer `object-upload-v1` gets today's chunk PUTs. A direct session sends each chunk grant -> `PUT` to the storage link (`ApiClient::put_to_storage`, on the upload storage client: no default headers, cookies, `Authorization` or redirects, https only) -> commit (`direct_upload::upload_chunk`); every decision (answer validation, per-chunk retries, the 4-grant cap) is core's `direct_transfer::upload`, the CLI only does the HTTP. A session's transport never changes after init: a direct session that cannot finish (a node without the routes, a refused link, storage failing four times for a chunk) is abandoned and the file inits again WITHOUT the token and goes through the API. That happens once per file per run: the file keeps its own `direct_given_up` bit (a memory that expires must not be what bounds the loop), and no further direct upload is started in that process, for that API base, for the trust period (`ApiClient::direct_upload_failed_recently`, counted on the monotonic clock: a wall-clock step neither ends the hold early nor stretches it), so a server where direct is broken costs the files already in flight when the first one gives up, not every file. The resume record carries `direct`, so a resumed upload continues on the transport it began on, and a recorded direct session is given up ONLY on a definite no (`--transport api`, or discovery that lists no upload / a JSON 404). If the capabilities cannot be read (`DirectOffer::Unknown`: a 5xx, a timeout, a bare 404) the file fails for that run with a message that names `--transport api`; if the login is not valid (`DirectOffer::Unauthorized`) it fails with the message of that case (no session: the usual "Not logged in"; a 401: `SESSION_EXPIRED_MESSAGE`; a 403: the server's error code and its status, e.g. `account_suspended, HTTP 403`, which is not an expired session); either way the session, its record and its committed chunks are kept. A 401/403 on the lookup is remembered for the LOGIN that was refused (a hash of the token) for a minute (`REFUSAL_HOLD`), and core's cache is not told: it would count a failed lookup, and two of them would park discovery (downloads too) for the whole trust period, whoever asks next, and a `bb login` could not undo that. So the same login is asked once, a login with another token at once, the same login again after the minute (a workaround for core's cache, which should not count authorization answers; it goes with that fix). Discovery is asked only when its answer is used (not for a resumed API session, nor for a file whose direct upload was already given up). Storage PUTs use `ApiClient::upload_storage_client()`, which has NO read timeout (reqwest's is one timer from send until the response, not reset while a request body goes out, so it capped every PUT at 60 s); a PUT is bounded by its own total timeout, 60 s plus the chunk at 128 KiB/s. What discovery said lives in a per-API-base state shared by every client of the process (`DirectState::shared`), so a daemon's per-resync clients do not ask again. `bb push --json` reports `transport` per file (`direct` or `api`), additive. **A test run must never reach production**: the CLI reads no `BB_API_BASE`, so a run with no `--api` and no config uses `https://api.beebeeb.io`. Set `BB_REFUSE_NON_LOOPBACK_API=1` on every run of the binary (it exits 2 for a non-loopback API URL before sending anything; `tests/api_guard.rs` reads every file under `tests/` (comments removed) and fails on a `Command::new(env!("CARGO_BIN_EXE_bb"))` whose command is run without `.env("BB_REFUSE_NON_LOOPBACK_API", ..)` and on any alias of `CARGO_BIN_EXE_bb`; it also fails on `.env_clear()`, `.env_remove(..)` of the variable, `.envs(..)` or a further `.env(..)` of the variable after the last guard, on any value but a literal `1`, on a spawn outside a fn body or in a helper module under `tests/`, and, for a command built in one function and run in another, on a file that clears the environment, adds a whole environment (`.envs`) or sets the variable to anything but `1` elsewhere; it is a text scan, so it fails closed (a sibling `.env_clear()` in such a file is flagged too) and cannot see `.env_remove(<constant>)`: the full suite in a network namespace is the backstop; its own fixtures prove each turns red) and give every run an explicit local `--api`; unit tests build clients with `ApiClient::new_for_test`, which refuses a non-loopback URL. Run the full suite on a machine where you can put it in a network namespace (`unshare -rn`) when a change touches how the API URL is chosen. Detail: docs/runbook/cli-task-history.md → "2173 direct S3 upload".

## Dependencies

`beebeeb-core` + `beebeeb-types` via Cargo git dependency pinned to a full 40-char SHA — not a floating branch. **Keep the pin aligned with `repos/server/CORE_REV`** (the deploy-verified snapshot); bump `rev` in both lines + `cargo build` + fix what the compiler flags, committed together. Non-exhaustive `match` on core enums is intentional (a new variant is a compile error). Local dev:

```toml
[patch."https://github.com/beebeeb-io/core"]
beebeeb-core = { path = "../core/beebeeb-core" }
beebeeb-types = { path = "../core/beebeeb-types" }
```

CI strips `[patch]` before building (see `release.yml`).

macOS `~/Library/Application Support/beebeeb/config.json`; Linux `~/.config/beebeeb/config.json`. Contains `api_url`, `session_token`, `master_key`, `email`. Guard like an SSH identity file.
